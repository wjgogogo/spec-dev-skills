# Refactoring UI

把用户任务转成清楚的视觉关系：重要内容突出，相关内容成组，辅助内容安静，操作容易发现。用有限且有差异的设计选项提高一致性。

## 确定工作模式

- **评审或解释**：保持只读。依据可见界面、实际状态或代码给出问题、影响和具体改法；代码推断与已观察的视觉问题分开报告。
- **设计或实现**：完成授权范围内的改进，并在实际内容和相关状态下检查结果。复用现有组件、token、品牌和技术栈。
- **从零设计**：先完成一个具体功能的最小可用流程，再决定导航和页面外壳；先确定内容与层级，再细化视觉。

已有其他工具或技能负责产出 HTML、设计稿或应用页面时，本技能提供设计判断，不替换其产出流程。不得仅因美化需要就重写产品、增加功能或建立新设计系统。

## 理解界面

从现有文件、截图或可访问页面确定：用户在完成什么任务、首先需要看到什么、主要操作是什么，以及当前信息密度、品牌、组件和响应式约束。实现前读取适用的仓库说明和现有样式约定。

有实际界面时先观察渲染结果；只拿到截图时，不推断不存在的交互或隐藏状态。仅有代码时可以分析结构与样式，但不能声称已完成视觉验收。缺少关键产品意图时再提问，能从上下文发现的信息自行查找。

## 选择改进

按当前问题选择相关准则，阅读 [references/design-principles.md](references/design-principles.md) 的对应章节：

| 现象 | 优先阅读 |
| --- | --- |
| 不知道从哪里开始、反复纠结样式 | 1. 从功能开始与有限选项 |
| 所有内容抢眼、主操作不明显 | 2. 视觉层级 |
| 拥挤、关系不清、宽屏浪费、窄屏挤压 | 3. 布局与间距 |
| 文字难读、对齐别扭、数字难比较 | 4. 排版 |
| 色板不够用、状态刺眼、文字对比不足 | 5. 颜色 |
| 浮层不清楚、阴影随意 | 6. 深度 |
| 截图不可读、图标粗笨、上传图片破坏布局 | 7. 图片 |
| 空状态无引导、边框繁杂、组件组织僵硬 | 8. 完成度 |

通常先解决任务与分组，再处理层级、排版、布局和颜色，最后做装饰。以当前最影响理解的问题为起点，不机械执行全套重设计。

修改建议应形成可验证的因果关系：**当前现象 → 对用户任务的影响 → 具体调整 → 如何检查**。选择足以解决问题的改动，避免为了展示技巧同时改变无关区域。

## 验证与交付

有渲染条件时，检查改动区域在相关桌面和窄屏宽度、真实长文本、适用空状态及关键交互状态下的表现。重点核对溢出、分组、阅读顺序、操作发现性和可读性；有影响才检查错误、禁用、选中、焦点等状态，不要求无关的全量回归。

- 视觉修饰不能损害语义结构、表单标签、键盘操作或必要的提示。
- 文字变浅后检查实际前景与背景的对比；用文字、形状等补充颜色表达。
- 保留信息密度和任务效率。不要把高密度工作台统一改成宽松的展示页面。
- 实现时执行项目已有、与改动相称的验证；截图或渲染检查与代码检查分别报告。

评审交付最值得处理的问题及具体改法，不罗列与当前界面无关的原则。实现交付改动、理由、验证结果和未验证部分。不能以构建通过、token 合理或想象中的效果代替视觉确认。

## 使用依据

方法提炼自 Adam Wathan 与 Steve Schoger 的《Refactoring UI》。参考文件是独立可用的操作准则；刻度和示例是起点，已有项目规范与用户明确要求优先。
